# 报错与现象对照表

| 现象 / 报错 | 原因 | 处理 |
|---|---|---|
| `没能从 xxx 检测到地理范围` | 没有世界文件、GeoTIFF 标签或可识别侧车 | `inspect` 看 `crs` 是否识别；用 `--bounds 西,南,东,北` 补齐，米制坐标再加 `--source-crs 3857` |
| `输入 GeoTIFF 的坐标系是 EPSG:xxxx，本工具只支持 4326 与 3857` | 源是 UTM/高斯克吕格等 | 先用 `gdalwarp -t_srs EPSG:3857` 重投影，不要伪造范围 |
| `预计生成 N 个瓦片，超过 30 万保护阈值` | 层级或范围过大 | 先 `--dry-run` 看计划；缩小范围、降低 `--maxzoom`，确认后加 `--force` |
| `输出目录 xxx 非空` | 防误覆盖 | 换目录；确认可清空后加 `--force` |
| `按当前范围与层级没有可生成的瓦片` | 范围反了，或层级被 `--zooms` 限制到无交集 | 检查 `--bounds` 是否 西<东、南<北 |
| `拼接后约 N 像素，超过内存保护阈值` | 瓦片目录拼整幅图过大 | 改用 `tile` 直接转格式，不必先拼大图 |
| `导出尺寸 N 超过 6 亿像素` | `--scale 1` 但源图极大 | 加 `--scale 0.5` 或 `--max-size 20000` |
| `--bounds 需要 4 个数（西,南,东,北）` | 顺手写了 `[w,s,e,n]` 或带括号 | 用逗号或空格分隔的裸数字 |
| `--split 格式应为 2 / 3 / 4 或 2x3` | 传了 `2*2` 以外的写法或 0 | 用 `2`、`3`、`4`，或 `行x列` 如 `2x3` |
| `xxx 里没有找到 z/x/y 结构的瓦片` | 目录层级不是 `<z>/<x>/<y>.png` | 确认根目录选对；有些下载器多套了一层，把上层目录传进来 |
| `无法读取 MBTiles` | 文件损坏或不是标准表结构 | 用 DB Browser 打开确认有 `tiles` 与 `metadata` 表 |
| 预览页白屏 | 用 `file://` 直接双击打开 | 在输出目录跑 `python -m http.server 8000`，访问 `http://localhost:8000/preview.html` |
| 预览页提示"无法加载 Leaflet" | 无外网，CDN 不可达 | 瓦片本身没问题；改用 QGIS 加载 `tiles/{z}/{x}/{y}` 或本地 Leaflet 副本 |
| 边缘有一圈透明/白边 | 范围不是整瓦片，补边所致 | 正常现象；JPEG 恒为白底，要透明就用 PNG |
| 瓦片上下颠倒 | 输入是 TMS 命名 | 加 `--input-tms` |
| 影像整体偏移百米级 | GCJ-02 基准面差异 | 见 `alignment.md`，用 `--bounds-datum gcj02`，不要改 bounds 硬凑 |
| 放大后模糊 | 超过 `native_zoom` 的层级只是插值 | 降到 `inspect` 给出的层级，或明确告知用户这是 overzoom |
| `verify` 报 zN 期望 X 个瓦片，实际 Y 个 | 生成中断或目录被改过 | 重跑到新目录；确认磁盘空间足够 |
| 内存占用飙升 / 进程被杀 | 源图过大（>2 亿像素） | 先 `export --scale 0.5` 降采样，再切 |
| 中文文件路径报错 | 控制台编码非 UTF-8 | 用 `-X utf8` 运行，或 `set PYTHONIOENCODING=utf-8` |

## 改动脚本后

```bash
<py> scripts/selftest.py
```

端到端自检覆盖：世界文件识别、4326/3857 判定、切片几何对齐（由瓦片像素反算经纬度与理论值比对）、MBTiles 与 TMS 输出、瓦片目录回流、分幅合计范围、GCJ-02 往返。全部通过再交付。
