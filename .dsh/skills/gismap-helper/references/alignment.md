# 对齐与偏移排查

切片"看起来偏了"几乎总能归到三类原因，按顺序排查，不要直接改 `--bounds` 硬凑。

## 一、坐标系（4326 还是 3857）

| 表现 | 说明 |
|---|---|
| 范围数值在 ±180 / ±90 内 | 经纬度，`EPSG:4326` |
| 范围数值达百万级 | 墨卡托米，`EPSG:3857` |

脚本按绝对值自动判定。判错时（例如赤道附近小范围的米制坐标恰好小于 180）用 `--source-crs 3857` 强制指定。

输出瓦片永远是 Web 墨卡托 XYZ，与谷歌/天地图/OSM 的瓦片网格严格一致。源是 4326 时脚本会做墨卡托换算，包括经度线性、纬度非线性的处理。

## 二、基准面（GCJ-02 偏移）

这是国内最常见的"偏移"来源，也最容易被误判成切片 bug。

- 谷歌卫星影像、GPS、WGS-84 底图：同一套坐标。
- 高德、腾讯、谷歌中国道路图：GCJ-02（火星坐标），相对 WGS-84 有 100~600 米的非线性偏移。
- 百度：BD-09，在 GCJ-02 上又叠了一层。

**判断方法**：问用户拿什么底图比对。

- 与 GPS 点、谷歌卫星、天地图影像比对 → 用 WGS-84，不做换算。
- 与高德/腾讯底图叠合 → 必须换算，否则一定偏。

用法：

```bash
# 用户给的范围是 GCJ-02（从高德/腾讯抄来的），切片时反算成 WGS-84
<py> gismap.py tile "图.jpg" -o out --bounds 116.32,39.91,116.36,39.94 --bounds-datum gcj02
```

换算公式在脚本里是标准实现，往返误差约 1e-13 度，可放心反复调用。

## 三、范围本身错了

排除了前两项仍偏，才是范围问题。症状是**整体按固定比例缩放或平移**，而不是局部扭曲：

- 宽度对了但位置偏 → 只有 `west/north` 错，检查世界文件的 C/F 是否被当成左上角**角点**而非**像素中心**（差半个像素，通常看不出来，但几十公里级会明显）。
- 明显被拉伸 → 把米制数值当成了度，或把 x/y 分辨率搞反。

## 验证手段

1. **`verify --source`**：`center_tile_mae` 是中心瓦片与源图重渲染的平均绝对差（0~255）。小于 8 基本无问题；超过 12 说明切片链路有错位。注意它只能证明"瓦片和源图一致"，证明不了"源图范围是对的"，所以要配合第 2 条。
2. **预览页叠加在线底图**：打开 `preview.html` → 勾选"叠加在线底图比对"。影像与 Esri 底图的路网/地物对得上，说明范围正确。这一步是对"范围是否对"的唯一直接检验。
3. **已知点核对**：找图上特征明显的地物（路口、桥），把它的瓦片号换算成经纬度，与实际坐标比。瓦片号 → 经纬度：

```
lon = x / 2^z * 360 - 180
lat = atan(sinh(pi * (1 - 2*y/2^z))) * 180/pi
```

## 不要做的事

- 用 `--bounds` 里加减零点几度去"修" GCJ-02 偏移。GCJ-02 是空间变化的非线性偏移，常数平移只能让某一小块对齐，别处会更歪。
- 在没排除基准面问题前重切一遍。切一百次也改不了 datum 差异。
